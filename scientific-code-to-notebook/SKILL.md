# Scientific Code → Researcher-Friendly Notebook

## 核心目标

将**已有复杂科研代码**改造成研究者能逐步读懂、独立运行、验证和修改的 Notebook，而非通过封装隐藏复杂性。保留经验证的科学定义、结果、输入条件和质量控制；适用于遥感、生态、气象、材料、生医、统计、工程、经济等学科，**不得把特定领域的数据格式和指标写成通用必需条件**。

## 何时使用

- 现有代码分散在多个脚本/函数/类中，科研人员无法追踪算法步骤。
- 希望把 Python/R/MATLAB/Julia 等遗留科研流水线变成可读 Notebook。
- 需要“单一研究问题/单一指标或算法一个 Notebook”，并希望对科研图表细节直接动手。
- 要保留论文/方法出处、数值一致性、输入输出可追溯和批处理能力。

若仅需要修改已有图件，优先使用配套 `scientific-figure-workflow`；若只要求审计算法正确性，用 `scientific-reproducibility-audit`。本技能可独立使用，不依赖另外两个技能已安装。

## 永远遵守的底线

1. **先审计，后重构。** 先阅读源码、参数、数据约定、现有输出、测试、方法论文与作者代码，再建立映射。不得读不到源码却声称已复现。
2. **算法保真。** 不改公式、指标定义、阈值、单位、聚合口径、随机过程及 QC；发现疑点时另列修复建议，不在重构中静默修复。
3. **不凭空造方法/引文/测试结果。** 每项科学算法必须有真实来源；找不到出处则标为 `待核验` 并暂停“忠实复现”的宣称。
4. **可读性优先。** 将科研关键步骤写在对应 Notebook 的连续、注释清晰的单元格里；仅把稳定且重复的 I/O、验证、缓存等功能保留为简短公共辅助代码。
5. **可重复执行。** 重开 Kernel 后按序执行可运行；每个指标 Notebook 在公共预处理完成后可独立运行，不依赖其他 Notebook 的内存状态。
6. **绘图与重计算解耦。** 图表单元从保存的数值表/必要中间数据重新绘制；调整字、颜色、图例、坐标轴时无须重新处理大型数据。绘图单元必须先断言输入数据非空——空数据出图按 FAIL 处置，不得静默保存空图。
7. **科学边界可见。** 明确观测值与真值、缺失与零、算法估计与独立验证、统计推断层级、平台/批次/样本依赖。
8. **不破坏原始成果。** 原文件、已验证结果不可覆盖；先版本备份或分支，结果写入新目录。

## 工作步骤

### 1. 盘点并锁定基线

扫描入口脚本、调用关系、原始数据/元数据格式、计算依赖、输出、测试、运行环境、论文引用。记录输入哈希、Git commit、参数、基线数值与缺失 QC。制作 **原函数/脚本 → 对应 Notebook 单元** 映射。同时枚举原实现输出的**每一个字段**（含 PlotID 等标识符字段的变换规则，如后缀剥除、大小写、命名映射），逐字段登记“已移植/已知差异”，并指定联合主键、检查唯一性与键集合；不按行号或仅交集比较。

按需阅读 `references/audit-and-planning.md`。若来源和基线不可获得，先明确缺口并完成可做的整理，不报告未经验证的成果。

### 2. 划分独立分析单元

规划一个通用公共预处理入口（在有重复预处理需求时），按**科学研究单元**设置独立 Notebook：指标、模型、实验环节或图件。允许同一算法产生紧密耦合的多个指标共同放在一个 Notebook，不机械按文件个数拆分。

在 Notebook 内展示核心算法：输入筛选 → 中间变量 → 关键数学步骤 → 质量控制 → 输出。**不要把算法主体埋进多层 `.py` 调用。** 重计算、缓存和绘图边界必须显式可见。

参考 `references/notebook-design.md` 与 `references/project-layout.md`。

### 3. 保守迁移算法

逐项将原实现映射到 Notebook。对于原 R/MATLAB/Julia/C/C++ 算法：仅在已具备公式、测试与可比结果时做 Python 迁移；否则先由 Notebook 明确调用原语言环境/可执行程序并留存版本，不能把“封装调用”宣称为纯 Python 复现。

按项目实际规模写方法卡；仅登记适用且可核实的来源字段，不要求所有方法同时有 DOI、公式和官方源码。每项算法写方法卡：原始文献/DOI/页码/公式/官方源码版本、输入条件、参数、单位、默认值、适配说明、验证状态。方法卡模板见 `assets/method_registry_template.csv`。

### 4. Notebook 采用固定教学式顺序

每个分析 Notebook 至少有：

1. 研究问题、指标含义与适用边界（Markdown）。
2. 论文依据、原实现映射、数据依赖与参数说明。
3. **集中可编辑参数**（数据路径、样本、算法合法参数、绘图独立参数）。
4. 输入与 QC：单位、坐标、缺失、分组、有效样本数、版本。
5. **显式的核心计算步骤**：小而连续的代码单元、中文注释、必要中间量。
6. 计算诊断、数值验证、结果表保存。
7. **绘图阶段：重新读取已保存的表/矩阵**；一图一单元或明确小节。
8. 结果导出、解释范围和复现说明。

交互指清晰可编辑的参数、图表及可选轻量 `ipywidgets`，**不要求将所有环节做成复杂 UI**；交互控件不应产生隐藏状态或替代 Notebook 普通执行。

### 5. 科研图表工作流

对每类结果至少考虑计算诊断图和论文结果图；并非每个参数都需产生固定数量的图。每图拥有独立标题、显式 Matplotlib/合适绘图库绘图段、顶部可编辑样式参数；按任务或投稿要求输出 `SVG/PDF/PNG` 中所需格式和生成图所用数据，注明分辨率、单位、误差含义和图件来源。图内文字含非拉丁字符（如中文）时必须显式配置含相应字形的字体族；交付的 Notebook 输出中不得残留缺字形（Glyph missing）渲染警告。每张图保存后复核：图非空、绘图数据行数与预期一致。详读 `references/figure-guidelines.md`。

### 6. 复现验收

使用原数据、相同算法参数和相同科学定义进行新旧结果对照。包括：确定性结果容差，浮点/并行/随机算法的可解释差异，字段/单位/分组一致性，缺失/QC 状态一致性，敏感性试验和可追溯运行记录。**图件与字段同样进入统一验收矩阵**：每张图按统一协议登记非空、有限绘图值、缺字形警告、绘图数据行数与视觉检查，未检查项保留 NOT-RUN；原实现每个输出字段（含标识符变换）逐字段核对，不得只对照数值指标。

**不得把所有差异简单用“浮点误差”解释。** 检查数据选择、坐标/时间对齐、版本、随机数、精度与顺序。阅读 `references/verification.md`。

### 7. 交付与维护

在统一 `output/` 下按预处理/分析模块/指标/图件/验证分组保存。每份图件应有绘图输入或不可再压缩的必要中间数据；重绘不应需要原始全量计算。写 `README` 说明从头运行、仅绘图运行、环境复建及结果目录。

**最终报告必须区分：已运行通过、未运行、待验证、不适用。** 若数据/运行环境缺失，交付结构与代码草案并明确未测试状态。

## 最终验收问题

- 科研人员能在 Notebook 里找到并解释每个关键公式对应的计算吗？
- 从干净 Kernel 可以运行吗？每个指标可以独立执行吗？
- 仅改一张图的风格时可以跳过昂贵算法吗？
- 结果与原算法比较是否有逐指标记录？不一致之处是否明确？
- 是否保留已知缺失值、QC、置信程度和统计独立性限制？
- 数据、参数、文献版本、环境及图片能否溯源？
- 每张图是否确认非空、无缺字形渲染警告、绘图数据行数与预期一致？
- 原实现每个输出字段（含 PlotID 等标识符的变换规则）是否逐字段移植或记录差异？

## 验收协议与执行边界

数值对照、缓存或独立绘图交付前，读取 [结果对齐与验收协议](references/result-contract.md)，使用 [统一验收表](assets/validation_matrix_template.csv)。按主键对齐、预先确定容差、核对缺失与 QC；遵循协议的总体状态判定。技能可独立安装，无须其他技能目录。运行环境缺失时说明限制，不宣称已执行。
