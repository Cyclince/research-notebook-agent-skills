# 可读 Notebook 的设计原则

## 组织

- 每个 Notebook 表达一个可解释的科学单元：一个指标、一组耦合计算、一个模型或一个科学问题。
- 同一 Notebook 由 Markdown + 可读代码交替构成，标题稳定，附方法参考和公式对应关系。
- 尽量使用 `01_加载` / `02_检查` / `03_计算` / `04_验证` / `05_保存` / `06_绘图` 等有序小节。
- 参数集中，但**科学算法参数**与**绘图样式参数**分离；禁止调整图形时意外改变计算。
- 同一 Notebook 前后顺序独立、在 kernel 重启后可复现，不读取别的 Notebook 内存变量。
- 日常配置使用纯 YAML/简单 Python 字典；避免复杂依赖注入框架或层层类继承。

## 什么时候适当使用函数

适宜：标准数据读取、路径检查、缓存/文件保存、重复的小型数值辅助过程、可验证的昂贵底层库调用。
不宜：把核心论文算法藏在 3–6 层 `calculate_all(...)`、类方法、回调中，而 Notebook 只有一行调用。

> 保留必要函数，不是禁止函数。核心科学公式需在 Notebook 可见并配解释，也可通过 `inspect`/源码链接暴露作者原始实现以便核查。

## Markdown 旁注样式

在每个公式/核心步骤旁说明：

- **为什么**需要这步？其科学目的是什么？
- **输入是什么**，是否为原始观测、代理变量或推断值？
- **论文出处**（准确 DOI、公式/章节或代码 commit）。
- **可调参数**、单位、有效范围以及改变参数的影响。
- **产物是什么**，单位和 QC 含义。
- **不能如何解释**，尤其相关不等于因果，代理指标不等于真值。

## 交互性

- 第一优先级：清楚的参数单元 + 分阶段运行 + 独立图表代码。
- 只有当滑块/下拉框真正提高诊断效率时，才考虑 `ipywidgets`。
- Widgets 不能成为唯一入口；无交互插件时依旧可以通过配置复现。
- 大计算加缓存标志 `RECOMPUTE = False`；缓存必须与数据及科学参数关联，不能用旧缓存冒充新的参数结果。

## 跨语言

- Python → Notebook：可将核心算法显式呈现，引用原函数留对照。
- R/MATLAB/Julia → Notebook：优先以可重现的环境内调用原语言实现，或经公式和结果验证后移植 Python。
- Fortran/C/C++ 等性能内核：保留已验证外部调用并展示方程、输入输出和版本；无需强行翻译成纯 Python。
- GPU 或远程计算：Notebook 管理清楚的配置、运行参数及结果读取，避免虚报本地可执行性。
